# 000 理念：授权的工作与更少的打断

这个仓库把「游戏工作室」做成一台只在 GitHub 上工作的机器。人保留三种动作：在 issue 或 PR 里提需求、回答一个只有人能回答的问题、合并 PR。其余的部分交给成文规则和 worker。

判断每一处设计的标准只有一条：它花掉的注意力是否少于它带来的价值。一条消息、一个面板条目、一个设置项、一段文档都算成本；没有一个具体的人会因它而行动，它就应当消失。

## 为什么工作室跑在「授权的工作」上

注意力和预算一样有限。所以工作必须先有来源，才允许开始：

- **有人明确要求。** issue 或 PR 里 @ agent 的人必须在允许名单上；不在名单上的人，消息被忽略而不是排队等待。在旧正文里补一个 @ 不会变成新要求，要发新评论。
- **有成文规则允许。** 没人点名时，只有写在 `seed/policy.json` 里的规则才能让工作开始。规则用英文写、每条有 id、可以逐条审查，不是模型的直觉。
- **推断的工作先记录。** 三个工作室 Source（证据、CI、工程）发现的「欠账」不带人的授权，只能成为推断候选。`eval.mode` 为 `observe` 时，评估结果只记为「本来会接单」，不会真的开单；切到 `auto` 才会自动接。

这一套由 dsh-superagent 的授权模型实现（外部依赖，版本固定在 [compat.json](../compat.json)）；工作室补的是规则、提示段、剧本和三个主动 Source。读 [001-domain.md](001-domain.md) 可以看到每个概念落在哪里。

## 三个原则

### 1. 只在被要求、或有成文规则允许时行动

- 被要求 = 直接对 agent 说话，且发送者在允许名单上。
- 有成文规则 = 规则先写下来，再让 agent 遵守。`seed/policy.json` 的每一条都写明何时匹配、能写什么、产出什么、什么时候停下；`observe` 模式让人先看判断，再决定是否放权。
- 「看到 main 红了就顺手修」不是原则，是越权。`studio-ci` 只把红色运行变成候选，接不接由规则和模式决定。
- 范围是硬的。写入边界之外的改动，即使明显正确，也是缺陷；需要越界时停下来说明，而不是改完再解释。

### 2. 只在有人必须行动、或能用到结果时说话

- 开帖时声明这是自动代理（[communication.md](../seed/prompts/communication.md) 的第一行），之后不再重复签名。
- 工作期间安静。有结果、需要决定、做不了，才写第二条。
- 需要决定时只问一个问题：发生了什么、两三个选项、推荐哪个、一句为什么。不猜，不连问，不问「要继续吗」。
- 结果写在工单上，不私聊。故事文件与证据目录是仓库里的持久上下文，跨会话可读。
- 噪音大时改提示词或收紧规则，不要用更多消息解释噪音。

### 3. 先有证据，才说完工

- 证据只能是这台机器上真实运行的产物：`capture_command` 写出的 PNG、`test_command`/`run_command` 的日志、证据索引里以 `Run result:` 开头的那一行。
- `OBSERVED — …` 才能关故事；`NOT VERIFIED — …` 是一次诚实的报告，不是完成；`N/A — …` 只用于没有运行时可观察行为的工作。
- 这条线由插件兜底：[guard-docs](../packages/studio/src/guard/docs/index.ts) 在写入后检查故事是否有 `status` 与 `## Acceptance`、`done` 是否真有证据、PNG 是否小于 1024 字节、证据索引是否缺 `Run result:`。被拦下的写入要改对，不是绕过。
- 没有证据的 PR 是草稿。PR 四节正文（What changed / Verification / Evidence / Risks and not covered）不是格式要求，是让审阅者不用追问的压缩方式。

## 与「每步等批准」的聊天助手对比

聊天助手把判断成本留在每一步：它先问「我可以改这个文件吗」，改完再问「要继续吗」。人被迫在信息最少的时候做最多的决定，而它给出的确认不携带任何新信息。

工作室把判断前移：规则写一次，之后每一步由规则回答；人的注意力只用来处理规则没覆盖的岔路。

| | 每步等批准的聊天助手 | 这个工作室 |
|---|---|---|
| 触发 | 人每轮输入 | 一次请求，加上成文规则；推断候选先记录 |
| 打断频率 | 每个动作一次 | 只有必须人拍板时一次 |
| 问题的形态 | 「要继续吗」 | 「A 还是 B，我建议 A，因为……」 |
| 判断在哪 | 每步重新问人 | 事先写进 `seed/policy.json`、提示段、剧本 |
| 完成判定 | 助手说自己做完了 | PR 关闭，且证据是 `OBSERVED` |
| 失败 | 停下来等人猜 | `blocked` 加具体原因，人回一条即可恢复 |

一句话：把人从「每一步的批准者」变成「规则的作者和结果的审阅者」。

## 这一页对操作者意味着什么

- 从窄开始：允许名单短、`eval.mode` 用 `observe`、并发从 1 起。看十张真实工单，再逐条放权。
- 读它写的东西。写错了改提示段或规则，不要替它补一条机器人评论。
- 一个部署只对应一个游戏仓库；多个仓库就是多个部署。
- 它用一个团队每天都看到的账号说话，所以它说的话由你负责。授予的能力越多，操作者欠团队的注意力管理就越多。

规则本身在 [002-work-types.md](002-work-types.md)；规则如何被执行在 [003-playbooks.md](003-playbooks.md)。
